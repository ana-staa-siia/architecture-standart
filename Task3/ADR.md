### **Название задачи:** Выбор концептуальной архитектуры для MVP онлайн-открытия депозитов
### **Автор:** Архитектор команды цифровой трансформации
### **Дата:** 2025-10-20
### **Контекст**

Банк "Стандарт" столкнулся с необходимостью цифровой трансформации для привлечения клиентов молодых категорий. Ключевая бизнес-задача — позволить клиентам открывать депозиты и накопительные счета онлайн, через сайт и интернет-банк. Текущий процесс открытия депозита в отделении неэффективен, задействует ручной труд сотрудников бэк-офиса (расчет ставок в Excel, обмен email) и занимает до часа.

Существующая IT-архитектура не поддерживает эту функциональность:

Интернет-банк — монолит, не интегрированный с процессом депозитов.

АБС перегружена и не должна нагружаться прямыми запросами из онлайн-каналов.

Данные о ставках разрознены и не централизованы.

Цель — реализовать MVP, в котором клиент может подать заявку на депозит онлайн, а обработка заявок в фоновом режиме продолжается сотрудниками бэк-офиса по адаптированному процессу.

Портал бэк-офиса отправляет команду в Сервис депозитов.<br>5. Сервис депозитов публикует событие "Команда на открытие депозита".<br>6. Сервис депозитов получает событие и обновляет статус заявки.<br>3. Сервис депозитов инициирует отправку SMS-уведомления клиенту через СМС-шлюз.|

### **Нефункциональные требования**

|  **№**  |**Требование**|
|:-------:| :- |
| **+R1** |Изоляция АБС: Прямые синхронные вызовы API АБС из онлайн-каналов запрещены. Все взаимодействие должно быть асинхронным через брокер сообщений.|
| **+R2** |Доступность: Критичные компоненты (Сервис депозитов, Интернет-банк) должны обеспечивать доступность 99.9%.|
| **+R3** |Производительность: Время отклика операций в интернет-банке не должно превышать 500 мс для 95% запросов.|
| **+R4** |Масштабируемость: Новые сервисы должны поддерживать горизонтальное масштабирование.|
| **+R5** |Безопасность: Все передаваемые конфиденциальные данные должны шифроваться с использованием TLS 1.2+.|
| **+R6** |Технологическая совместимость: Новые сервисы должны использовать существующие в банке технологии (Java, .NET, MS SQL, Oracle) для минимизации затрат на обучение.|
| **+R7** |Поддерживаемость: Архитектура должна допускать постепенную декомпозицию монолита интернет-банка.|

### **Решение**

**Логика принятия решений:**

1.  **Изоляция АБС (+R1):** Введен брокер сообщений (Kafka) как центральная шина для всех команд и событий, связанных с АБС. Это обеспечивает буферизацию и асинхронность.
2.  **Централизация логики:** Создан отдельный Сервис депозитов, который инкапсулирует всю бизнес-логику по работе с депозитными продуктами и заявками. Это позволяет развивать функциональность независимо от монолитов (+R7).
3.  **Производительность (+R3):** Для обеспечения низкой задержки в Сервис депозитов встроен кэш (Redis) для хранения каталога продуктов и справочников.
4.  **Технологический выбор (+R6):**
    - Сервис депозитов реализуется на Java Spring Boot (есть экспертиза от команд АБС и кол-центра).
    - БД заявок - MS SQL (совместима с текущим стеком интернет-банка).
    - Для интеграции с монолитным интернет-банком используется REST API (наиболее совместимый протокол).

### **Альтернативы**

**Альтернатива 1: Прямая интеграция интернет-банка с АБС**
- *Описание:* Монолитный интернет-банк напрямую вызывает API АБС для открытия депозитов.
- *Причина отказа:* Нарушает +R1 и +R2. Создает риск перегрузки АБС и низкой отказоустойчивости.

**Альтернатива 2: Размещение логики в самом интернет-банке**
- *Описание:* Вместо создания отдельного Сервиса депозитов, вся логика реализуется внутри монолита интернет-банка.
- *Причина отказа:* Усложняет развитие монолита (+R7), не решает проблему производительности (+R3) и создает сильную связность.

**Недостатки, ограничения, риски**

**Недостатки:**
- **Усложнение инфраструктуры:** Требуется развертывание и сопровождение новых компонентов (Kafka, Redis, новые сервисы).
- **Повышенные операционные затраты:** Необходимы специалисты для поддержки распределенной системы.

**Ограничения:**
- **Сложность отладки:** Распределенная система сложнее для отладки и трассировки запросов, чем монолит.
- **Согласованность данных:** Реализация в конечном счете согласованной данных между БД заявок и АБС требует дополнительных усилий.

**Риски:**
- **Риск производительности Kafka:** При неправильном планировании мощности Kafka может стать узким местом.
- **Миграция данных:** Необходимость переноса логики расчета ставок из Excel в новый сервис может быть нетривиальной задачей.
- **Сопротивление изменениям:** Команды могут сопротивляться переходу на новые технологии и практики разработки.
