
### **Название задачи:** Интеграция передачи ставок по депозитам в кол-центры
### **Автор:** Архитектор команды цифровой трансформации
### **Дата:** 2025-10-20

### **Функциональные требования**

|**№**|**Действующие лица или системы**|**Use Case**|**Описание**|
| :-: | :- | :- | :- |
|**UC-1**|Сотрудник кол-центра, CRM кол-центра, Сервис ставок|Консультация по текущим ставкам|1. Клиент звонит в кол-центр с вопросом о ставках по депозитам.<br>2. Сотрудник кол-центра открывает раздел со ставками в CRM.<br>3. CRM запрашивает актуальные ставки из Сервиса ставок.<br>4. Сотрудник консультирует клиента на основе полученных данных.|
|**UC-2**|Администратор ставок, Сервис ставок, Партнерский кол-центр|Автоматическая выгрузка ставок для партнера|1. Администратор обновляет ставки в Сервисе ставок.<br>2. Сервис ставков автоматически генерирует файл с актуальными ставками.<br>3. Файл передается по SFTP на сервер партнерского кол-центра.<br>4. Система партнера импортирует данные из файла.|
|**UC-3**|Сервис ставок, CRM кол-центра|Кэширование ставок в CRM|1. Сервис ставков публикует событие об изменении ставок.<br>2. CRM кол-центра получает событие и обновляет локальный кэш.<br>3. При запросе сотрудника данные возвращаются из кэша без обращения к сервису.|

### **Нефункциональные требования**

|**№**|**Требование**|
| :-: | :- |
|**NFR-1**|Доступность данных о ставках: 99.5% в рабочее время кол-центра|
|**NFR-2**|Актуальность данных: максимальная задержка обновления ставок - 5 минут|
|**NFR-3**|Безопасность: передача файлов должна использовать шифрование (SFTP/SSL)|
|**NFR-4**|Отказоустойчивость: при недоступности сервиса ставок CRM должна работать с последними известными данными|
|**NFR-5**|Производительность: время получения ставок сотрудником - не более 2 секунд|

### **Решение**

**Архитектурный подход:** Реализовать двухуровневую систему распространения ставок:
1. **REST API + кэширование** для внутреннего кол-центра
2. **Автоматическая выгрузка файлов по SFTP** для партнерского кол-центра

**Логика принятия решений:**
- Для внутреннего кол-центра используем синхронный API с кэшированием для производительности
- Для партнерского кол-центра используем файловый обмен из-за ограничений их системы
- Внедряем механизм уведомлений об изменениях для поддержания актуальности данных

### **Альтернативы**

**Альтернатива 1: Единый REST API для всех кол-центров**
- *Описание:* Предоставить партнерскому кол-центру доступ к REST API
- *Причина отказа:* Партнерская система не поддерживает API-интеграцию, только файловый обмен

**Альтернатива 2: Ручная выгрузка файлов**
- *Описание:* Администратор вручную выгружает и отправляет файлы партнеру
- *Причина отказа:* Не обеспечивает актуальность данных (NFR-2), высокая нагрузка на персонал

**Альтернатива 3: Репликация базы данных**
- *Описание:* Настроить прямую репликацию БД ставок в системы кол-центров
- *Причина отказа:* Нарушает границы систем, проблемы безопасности, сложность реализации

**Недостатки, ограничения, риски**

**Недостатки:**
- Два разных механизма интеграции увеличивают сложность поддержки
- Файловый обмен имеет задержку в обновлении данных

**Ограничения:**
- Партнерский кол-центр получает данные с задержкой до 5 минут
- Нет реального времени для партнерской системы

**Риски:**
- Риск рассинхронизации данных между внутренним и партнерским кол-центрами
- Риск сбоев в передаче файлов по SFTP
